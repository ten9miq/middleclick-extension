# 新タブ内でのナビゲーション再実行の検証

ChatGPTのプロジェクト欄の新規会話アイコンについて、学習済みURLや固定ルートを使わず、元タブの表示を保ったまま開けることを一時拡張で確認した。本番拡張には組み込んでいない。

## 方式

1. 元タブでは中ボタンイベントを抑制し、通常のクリック処理を実行しない。
2. コントロールのタグ・明示ラベル・祖先の安定したdata IDから識別情報を作る。
3. 元タブと同じURLを右隣のバックグラウンドタブに読み込む。
4. 新タブ内で識別情報が一意に一致するコントロールを待ち、そのタブ内だけで通常クリックを1回実行する。
5. 実際の遷移と表示を確認する。移動先URLの学習・保存は行わない。

プロジェクトIDからURLを組み立てる処理はない。識別アルゴリズムはURL規則に依存しないが、この試作の実行対象はChatGPTの日本語・英語のプロジェクト新規会話ボタンに限定している。他サイト全般への対応を確認したものではない。

## 実サイトでの結果

専用Google Chrome 156.0.8078.80、9223、viewport 1240×1051 CSS px、DPR 1.5で実施。入力は合成中ボタンイベントであり、物理マウス入力ではない。

| 条件 | 結果 | 所要時間 |
| --- | --- | --- |
| ホームから、展開済みプロジェクトAの新規会話アイコン | 成功 | 7,076 ms |
| 既存会話に未送信テスト文があり、会話本文を途中までスクロールした状態から、折り畳まれた別プロジェクトBの新規会話アイコン | 成功 | 11,036 ms |

所要時間はバックグラウンドでのページ読込み、対象の再識別、クリック後の完了確認用1,500 ms待機を含む。安定した性能測定や多数回の平均ではない。

両ケースで以下を確認した。

- 新タブは1件だけ増加し、元タブの右隣、active=false。元タブはactive=trueを維持。
- 新タブは元ページを読み込んだ後、対象操作を1回実行し、該当プロジェクトの新規会話入力欄を表示した。
- 元タブでは通常クリック0回、Navigation APIの遷移イベント0件。
- 元タブのURL・タイトル・履歴エントリーキー・history.stateが前後で一致。
- 表示中の本文・入力内容・選択状態のハッシュ、およびDOMノードの対応が前後で一致。
- 元タブのスクロール・ビューポート・フォーカスが前後で一致。
- 2件目では未送信テスト文の表示を維持し、本文scrollTop=1500、サイドバーscrollTop=62を維持した。
- 検証用service workerのwarn/errorは0件。

タブグループは両ケースとも未所属（groupId=-1）。グループ所属時の分岐はコードにあるが、今回実画面では検証していない。

snapshot・元タブのスクリーンショット・DOM比較で表示を確認した。私的な会話名・本文・個別URL・画像はこのフォルダーに保存していない。未送信テスト文を除去し、再読み込み後にも空であることを確認した。一時拡張をアンインストールし、作成した検証タブをすべて閉じた。

## 他の候補

- Ctrl付き合成クリック: 新タブは増えず、元タブがプロジェクト画面へ移動した。対象の上位クリック処理はイベント引数を使わない形だった。
- 静的URL取得: ボタンのDOM属性と、対象付近のReactプロパティで確認した範囲には、直接利用できるhref/to/url等がなかった。React内部全体を解析したという意味ではない。
- Navigation APIで元タブの遷移をキャンセル: 先行試験ではpush/replaceをキャンセルしてURL・履歴を保てたが、表示はプロジェクト画面へ変わった。

## 限界と本番化前の作業

- ユーザーの実操作でも、元ページが新タブに表示された後にプロジェクトへ切り替わる待ち時間が問題になった。元タブ保持の検証成功は、学習済みURLを直接開く方式と同等の速さを示すものではない。元ページの再読込みとアプリ初期化が必要なため、初回からの速さを重視する場合には不利。
- ページ再読込み分の待ち時間と通信・メモリー使用が増える。
- 元URLだけでは再現できないアカウント・展開状態などに依存し、新タブに対象が現れない場合は使えない。曖昧な対象は実行しない。
- 新タブでもサーバー上の変更は共有されるため、任意の更新・削除操作に無条件適用できる方式ではない。
- 今回は1アカウント・2プロジェクト・2つの元ページでの試作検証。全プロジェクト、他言語、他サイト、物理入力、連打、タブグループ所属時は未検証。
- このコードは検証用。ページ変更によるキャンセル、service worker再起動、タイムアウト時の後始末、重複操作、権限・対象範囲、ユーザーへの進捗表示などは本番用に設計する必要がある。

## 速度を優先する場合の別案

ChatGPT専用の例外を認める場合、所有するプロジェクトIDをDOMから取得し、`/g/<project-id>/project`を直接開く方法がある。先行2プロジェクトの通常操作で観測した移動先と一致し、別の第3プロジェクトでも、この形で組み立てたURLを新しい検証タブへ直接読み込むと該当プロジェクトの新規会話入力欄が表示されることを確認した。

これはサイト固有のURL規則に依存する候補であり、汎用的に任意のボタンの移動先を取得できる仕組みではない。今回の直接URL確認は、拡張の中クリック処理への組込みや同条件の速度比較を実施したという意味ではない。ユーザーの優先順位を確認するまで、再実行方式の試作をこの候補へ切り替えていない。

## 検証用ファイル

- `manifest.json` / `background.js` / `content.js`: 一時拡張。本番のmanifestやスクリプトは変更していない。storage権限・学習テーブルは使わない。
- `capture-source.js`: 元タブの状態とクリック・遷移回数の計測を開始する。MCPのevaluate_scriptのformat=functionで実行する。
- `compare-source.js`: 同じ元タブで状態の一致を判定する。表示本文・入力内容はハッシュ化して返す。
- 中ボタンイベントはリポジトリ既存の`scripts/synthetic-middle-click.js`に、最新snapshotの対象UIDを渡して送った。

これは独立した実験用拡張であり、通常のMiddleClick+の読み込み先ではない。再検証はAGENTS.mdとdocs/CHROME_DEVTOOLS_MCP.mdに従い専用Chromeで行い、一時拡張のIDを導入結果から確認して後片付けする。
