# イベント処理からの移動先解析

ChatGPTのプロジェクト新規会話ボタンを実行せず、現在読み込まれているJavaScriptとReactの保持値を調べ、5つの表示中プロジェクトについて移動先を抽出できた。これは手動で呼出関係を追った調査と限定的な抽出実験であり、汎用の自動解析機能を実装・本番組込みした結果ではない。

## 確認した処理

ReactのonClickはボタン直上ではラッパーだった。親コンポーネントの関数ソースまで追うと、概略は次の構成だった。

```js
// 説明用の擬似コード。実際の変数名や構造を固定するものではない。
onClick = () => {
  if (linkedLocalProject || localTaskMode) startLocalTask();
  else openProject();
};

openProject = () => {
  updateSidebarState();
  if (projectRouteEnabled || linkedLocalProject)
    navigate(projectUrl(projectId), { state: navigationState });
  else
    navigate('/', { state: { chatGptProjectId: projectId, ...navigationState } });
};
```

呼出先のURL生成関数は、引数のIDをencodeURIComponentに通し、`/g/<encoded-id>/project`を返す純粋なテンプレート関数だった。

この調査では、対象コンポーネントの実ソースからインポート先を追い、既に読み込まれているRspackのESMチャンク内のモジュール定義を確認した。観測時のコンポーネントはチャンク`87162.9b77714e1f.js`のモジュール`aDgv`、URL生成側は`WLgA`のexport `c`だった。これらは今回の観測値であり、将来の固定識別子として使えない。

## 実行せずに確認できた値

- 現在のボタンに対応する親Reactコンポーネントと、そこで生成されたクリック関数。
- React CompilerのmemoCacheに保持されたプロジェクトID・分岐フラグ・画面状態の有無。
- 対象5件すべてで、プロジェクトURLを使う分岐が有効、ローカルプロジェクト連携なし、ローカルタスク分岐なしだったこと。
- 保持されたIDと、対象ボタンの所有者DOMにあるIDの一致。

## 抽出実験の結果

URL生成関数のソースに含まれる単純なテンプレートをデータとして読み取り、引数をencodeURIComponentで埋めた。ボタンのonClick、openProject、navigate、状態更新関数は呼び出していない。ページAPIの差替えや実際の遷移からの学習も行っていない。

- 表示中の5プロジェクトで同じ解析が成立し、所有者IDの対応もすべて一致した。
- 先行試験で通常操作または直接URLで表示を確認済みの3件と、抽出結果が一致した。
- 残る2件についてはURL抽出までで、今回そのURLの表示試験はしていない。
- 調査タブはホーム表示のままで、調査用ボタンをクリックせずに抽出した。調査用タブは終了後に閉じた。
- 個別のプロジェクト名・ID・私的本文・認証情報・取得したチャンク全文はリポジトリに保存していない。

## 意味と限界

DOMにURLがないことだけを理由に、イベント側からの解析を除外するのは早かった。今回の実装には純粋なURL生成部分があり、そこだけを取り出す方向には実証上の根拠がある。元タブでのクリックや、新タブでの再読込み後の操作再実行を省ける可能性がある。

一方、今回の抽出は、親コンポーネント・import/exportの対応・React Compilerの保持値の関係を人が特定している。変数名・モジュールID・キャッシュ位置を固定したままでは更新に弱く、今回の調査を汎用自動解析の完成と扱えない。URLに加えて画面状態が必要な分岐や、ローカルタスク等の別操作も存在したため、すべてを同じURL規則で処理することもできない。

本番化する場合は、MAIN world側での読取りと拡張への伝達、限定的な構文解析、純粋な文字列生成・既知の変換・確定した分岐だけを扱う評価器、曖昧な場合の拒否または従来学習へのフォールバックが必要になる。サイトの任意のイベント関数を実行して調べる方式にはしない。コード解析結果は読込み時に準備し、中クリック時には現在の保持値を照合して直接開く設計が候補になる。
